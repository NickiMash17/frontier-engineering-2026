# Evaluation

This document is the authoritative description of the Tier A benchmark,
its ground truth, the methodology, and the results of the one full run
performed so far. Every number below traces to
`evaluation/results/2026-08-29T05-28-25-444Z/results.json`, generated by
`node scripts/evaluate.js`.

## Benchmark: Tier A (controlled fixtures)

Four self-authored `fixtures/*` repositories, real npm-installed packages
at real CVE-affected versions, each isolating one reachability scenario.
CVE and version data is real, pulled from OSV.dev, and where a version's
actual exploitability was not obvious from advisory metadata alone, it
was independently confirmed by running the real exploit payload against
the real installed package (see `docs/EXPERIMENT_LOG.md` Experiment 1).

| Case | CVE | Package@version | Scenario | Ground truth |
|---|---|---|---|---|
| `case-a-reachable-minimist` | CVE-2020-7598 | `minimist@1.2.0` | HTTP handler passes request-body array directly into `minimist()` | `REACHABLE` |
| `case-b-unreachable-minimist` | CVE-2020-7598 | `minimist@1.2.0` | Only used by a dev-only build script; server never imports it | `NOT_REACHABLE` |
| `case-c-condition-not-satisfied-lodash` | CVE-2019-10744 | `lodash@4.17.11` | `_.defaultsDeep()` reached by attacker input, but a `sanitize()` step strips the required `__proto__`/`constructor`/`prototype` keys first | `CONDITION_NOT_SATISFIED` |
| `case-d-indirect-minimist` | CVE-2020-7598 | `minimist@1.2.0` | Reachable only via one hop of indirection through a local wrapper module | `REACHABLE` |

Ground truth for every case is hand-authored in that case's
`ground_truth.json`, written before the advanced system was run against
it, and never adjusted after seeing the agent's output (Experiment 1's
correction was to the *fixture's chosen CVE/version*, made by independent
empirical testing, before the fixture was considered final -- not a
post-hoc adjustment to match an answer).

## Methodology

For each case, `scripts/evaluate.js`:
1. Runs `scripts/baseline.js` -- a deterministic, code-blind version-range
   match against `data/advisories/index.json` (itself pulled from real
   OSV.dev records, see `data/advisories/*.json`).
2. Runs the advanced agent (one headless Claude Code CLI call per case,
   `Read`/`Grep`/`Glob` only -- see `docs/ARCHITECTURE_DECISIONS.md`
   ADR-001) with the baseline's flagged CVE/package/version as context.
3. Compares both outputs against `ground_truth.json` -- the advanced
   agent's own stated `confidence` is recorded but never substituted for
   this comparison.
4. Independently re-verifies every cited `evidence[].file`/`lines` entry
   against the real filesystem (existence + line-count bounds) before
   counting it as valid evidence -- the agent's claim that a citation is
   accurate is not trusted on its own.

## Metrics

- **Risk-classification accuracy**: does the system correctly separate
  `REACHABLE` (real risk) from everything else (`NOT_REACHABLE`,
  `CONDITION_NOT_SATISFIED`, `UNCERTAIN` -- not an actionable risk)?
- **Exact verdict accuracy**: does the full 4-way verdict match ground
  truth exactly (only meaningful for the advanced system -- the baseline
  only ever outputs a binary `VULNERABLE`/`NOT_VULNERABLE`)?
- **False positives / false negatives**: on the risk-classification
  question above.
- **Evidence completeness**: fraction of cited evidence entries that
  independently verify (see Methodology step 4).
- **Cost / latency**: taken directly from the CLI's own reported
  `total_cost_usd` / `duration_ms`, not separately estimated.

## Results

| Metric | Baseline | Advanced |
|---|---|---|
| Risk-classification accuracy | 2/4 = 50% | 4/4 = 100% |
| Exact verdict accuracy | n/a (binary only) | 4/4 = 100% |
| False positives | 2 | 0 |
| False negatives | 0 | 0 |
| Evidence completeness (avg) | n/a | 4/4 = 100% |
| Total cost (4 cases) | $0 | $0.2636 |
| Avg cost per case | $0 | ~$0.066 |
| Avg latency per case | ~0 ms | ~30,152 ms |

**Reading these numbers honestly:** n=4 is a Tier A controlled benchmark,
not the ~15-20-case real-world Tier B benchmark committed to in
`docs/PROJECT_SELECTION.md`. A 100% score on four cases is evidence that
the core mechanism works, not evidence that it generalizes -- Tier B,
with real repos and genuinely ambiguous cases, is the next test and is
expected to surface failures Tier A could not (see
`docs/DAY1_IMPLEMENTATION_PLAN.md` Section 9 for what was predicted to
fail here and didn't, and `docs/ARCHITECTURE_DECISIONS.md` ADR-003 for
what that does and doesn't justify).

The baseline's two false positives (`case-b`, `case-c`) are the concrete,
measured version of the project's core claim: a conventional
version-match scanner flags both, and both are not actionable risks in
this application's actual code.
